# Frontend decisions

Reference: XCEL Fitness class schedule print view, https://widgets.mindbodyonline.com/widgets/schedules/ab110745ac4/print (observed 22 November 2026). The observations below apply to that print view, not necessarily to the provider's interactive booking pages. Screenshot: `evidence/reference-schedule.png`.

1. **Comparable cards.** Problem: schedule rows show class, type, instructor and time, but omit price, remaining seats and experience level. Decision: show price, time, duration, level and seats on each listing card. Alternative: put these facts on details only. Reason: visitors can compare before opening each class. Tradeoff: denser cards. Code: `Home` in `src/main.jsx`. Evidence: `evidence/app-desktop.png` and detail screenshot.
2. **Search and narrowing.** Problem: the observed print schedule presents long day-by-day rows with no search, type filter or sorting control. Decision: add search, type filter and sort that compose. Alternative: separate category pages. Reason: users can quickly find appropriate sessions. Tradeoff: more controls on mobile. Code: `Home` in `src/main.jsx`. Evidence: `evidence/app-mobile-cdp.png`; enter “yoga” and change sort.
3. **Recoverable selection.** Problem: the observed print view has no selection or review action, so it cannot carry a visitor from comparison to a booking outcome. Decision: persistent plan with quantity controls, calculated total, availability conflict feedback and confirmation block. Alternative: immediate one-class booking. Reason: customers can review multiple sessions and correct conflicts. Tradeoff: a longer flow. Code: `Plan` in `src/main.jsx`, `checkCapacity` in `src/rules.js`. Evidence: `evidence/app-plan.png`; add Kettlebell Lab, toggle changed availability, revisit plan.
